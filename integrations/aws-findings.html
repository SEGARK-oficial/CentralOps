AWS Security Hub e GuardDuty

Duas integrações para trazer os achados de segurança da AWS para o CentralOps, normalizados como OCSF 1.8 Detection Finding (2004).

IntegraçãoO que trazQuando usar
AWS Security HubAchados agregados em ASFF: GuardDuty, Inspector, Macie, IAM Access Analyzer, Config e os controles do próprio Security Hub (CSPM)A conta usa o Security Hub. É a escolha padrão: uma integração, todos os produtos
Amazon GuardDutyAchados de ameaça direto da API do GuardDuty (contas, EC2, S3, EKS, RDS, Lambda)A conta usa o GuardDuty sem o Security Hub

Com os dois ligados, os achados do GuardDuty chegam duas vezes (pelo Security Hub e direto). Escolha um.

Como funciona​

ItemSecurity HubGuardDuty

Frequênciaa cada 5 minutosa cada 5 minutos
Regiõeslista ou * (as habilitadas na conta, via ec2:DescribeRegions)lista ou *; região sem GuardDuty é pulada
Primeira coletaachados atualizados nas últimas 24 horasidem
Posição da coletapor região: o UpdatedAt mais novo lidoidem
Teto por ciclo50 páginas, somando as regiões; a região corrente grava a posição exataidem
DuplicadosId + UpdatedAtidem

Cada atualização de um achado é um evento. O GuardDuty soma ocorrências num achado existente e o Security Hub muda o workflow ou arquiva. Por isso o CentralOps trata Id + UpdatedAt como identidade: a mesma ameaça que se repete gera um evento novo, com activity_id Update.

Achado indexado com atraso não se perde. Cada consulta começa 15 minutos antes da posição salva, e a posição nunca passa do fim da janela menos 15 minutos. O que for relido é descartado pelo dedupe.

Security Hub com agregação entre regiões. Se a cross-Region aggregation está ligada, a região de agregação devolve os achados de todas. Informe só ela; listar as outras traria duplicados.

Pré-requisitos​

  • O serviço ligado na conta e nas regiões que você vai listar. No console: Security Hub → Go to Security Hub → Enable Security Hub, ou GuardDuty → Get Started → Enable GuardDuty, em cada região. O GuardDuty só gera achados depois de ligado; não há histórico anterior.
  • Leitura pelo papel cross-account do CentralOps. O passo a passo pelo console está em AWS: dar acesso ao CentralOps. O template do painel Acesso por papel AWS já inclui securityhub:GetFindings, guardduty:ListDetectors, guardduty:ListFindings, guardduty:GetFindings e ec2:DescribeRegions. O passo a passo do papel está em AWS CloudTrail: Opção A.

Com o papel criado à mão (ou com access key, legado), a policy mínima é esta. ec2:DescribeRegions só é usado com regiões *:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "LerAchados",
      "Effect": "Allow",
      "Action": [
        "securityhub:GetFindings",
        "guardduty:ListDetectors",
        "guardduty:ListFindings",
        "guardduty:GetFindings",
        "ec2:DescribeRegions"
      ],
      "Resource": "*"
    }
  ]
}

Várias contas de uma AWS Organization​

O passo a passo completo, pelo console e pela CLI, está em AWS: dar acesso ao CentralOps. Resumo:

O mesmo template serve como StackSet: o External ID é por organização do CentralOps, não por conta AWS, então todas as contas de um cliente usam o mesmo papel com o mesmo External ID. Na conta de gerenciamento (ou administradora delegada do CloudFormation):

aws cloudformation create-stack-set \
  --stack-set-name centralops-readonly \
  --template-body file://centralops-readonly-role.json \
  --capabilities CAPABILITY_NAMED_IAM \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false

aws cloudformation create-stack-instances \
  --stack-set-name centralops-readonly \
  --deployment-targets OrganizationalUnitIds=r-abcd \
  --regions us-east-1

O papel é global (IAM), então uma região basta. Com auto-deployment, contas novas da Organization ganham o papel sozinhas. A conta de gerenciamento não recebe instância de um StackSet service-managed; crie a stack nela à parte, se for coletar dela.

Duas formas de cobrir as contas:

  • Conta administradora delegada do serviço. Com o Security Hub ou o GuardDuty configurados com administradora delegada, uma única integração nessa conta recebe os achados de todas as contas membro.
  • Modo AWS Organization (Enterprise). Os cards Security Hub — AWS Organization e GuardDuty — AWS Organization criam um pai que lista as contas (organizations:ListAccounts) e, para cada conta aprovada, uma integração filha nesta mesma organização, assumindo o papel de mesmo nome e path na conta membro (o que o StackSet acima criou). Contas suspensas ou que saem da Organization têm a filha desativada no próximo sync. O papel do pai fica na conta de gerenciamento ou numa administradora delegada do AWS Organizations; crie a stack nela com AllowListAccounts=true. Na Community o pai é criado, mas nenhuma conta é importada. O modo Organization exige papel; chave fixa não é aceita.

Criar a integração​

  1. Vá em Coleta -> Integrações e adicione AWS Security Hub ou Amazon GuardDuty.

  2. Preencha:

    CampoO que informar
    ARN do papel ou Access Key IDO RoleArn da stack (ex.: arn:aws:iam::111122223333:role/CentralOpsReadOnly).
    Secret Access KeySó com Access Key ID.
    Regiões AWSSecurity Hub com agregação: só a região de agregação. Sem agregação, ou no GuardDuty: lista (us-east-1, sa-east-1) ou *.

  3. Testar conexão. Security Hub: lê 1 achado da primeira região (InvalidAccessException = o Security Hub não está habilitado ali). GuardDuty: procura o detector da primeira região.

  4. Salve.

O achado completo fica no raw.

Solução de problemas​

InvalidAccessException no Security Hub. O serviço não está habilitado na região consultada, ou a conta não é a administradora.

GuardDuty: Credencial OK, mas o GuardDuty não está habilitado em <região>. Não há detector nessa região. Na coleta, a região é pulada sem erro.

Achados duplicados. O Security Hub e o GuardDuty estão os dois ligados para a mesma conta, ou o Security Hub tem agregação e você listou várias regiões.

Limitações conhecidas​

  • Criar uma integração por conta automaticamente é Enterprise (modo AWS Organization). Na Community, use a administradora delegada do serviço ou uma integração por conta.
  • Security Hub em ASFF. O formato OCSF nativo do novo Security Hub (GetFindingsV2) não é usado.
  • Sem atualização de volta. O CentralOps não muda o workflow nem arquiva achados na AWS.
